# Reviewing an answer change

Save & continue and Explore deeper prepare a read-only consequence preview from the saved map and the exact proposed answer/state. When a change affects downstream reasoning, retained research or captured work, Explorer asks for confirmation before saving. Keep editing or Escape retains the exact draft, chosen state and editor selection. Ordinary leaf changes without those effects save directly; no-op saves do not create history or invalidate content. Acknowledging a current review flag does not invalidate descendants, but still requires confirmation if clearing the flag makes captured work stale.

The preview lists unique affected questions and structural directions, with 50 items per page and one shortest recorded path in 30-step pages. Tree exposure, explicit dependency paths and mixed paths are distinguished. Counts can overlap between tree and dependency categories. The same full-map traversal powers the preview and committed review flags, including cross-branch and mixed paths. This estimates reconsideration, not guaranteed real-world damage. Linked ADR impact is explicitly unavailable until associations exist.

Saved research lacks a complete retained context dependency set. Any changed answer/state therefore conservatively marks all retained research as needing reconsideration, including results without a recorded decision path. This does not create a question dependency or mark unrelated answers for review. Research text/evidence is preserved, and neither acknowledgment nor answer saving claims it was refreshed. Successful new research clears its own marker. The live panel, Markdown and selected offline-viewer research show the warning. Visual map exports omit research entirely.

Accepted generated questions in affected branches remain saved and need review. An existing staged question batch becomes stale when its captured sources change. Active research is discarded only after the changed answer commits, using the existing owned-helper cancellation. Research conversation freshness uses its existing captured dependencies. Saved briefs and handoffs, running artifact helpers, unsaved brief/handoff proposals and answer-check/challenge results are listed when their captured inputs become stale. New results invalidate an old confirmation; progress text alone does not. The attached question session is never stopped or steered by the preview.

## Freshness and storage

One transient preview per Explorer controller expires after 15 minutes. Its opaque single-use token binds file/journey identity, the complete normalized saved snapshot, proposed text and effective state, expansion intent, draft revision/journey and captured pending/staged work. Confirming under the document lock rechecks the proof and consequential draft before history preparation and immediately before replacement. Another writer, dependency change, journey switch, changed proposed edit or late proposal cannot reuse it. Discard and paged inspection never write the map. Failure before replacement preserves the prior saved document; existing history recovery handles post-commit failures.

The editor also binds confirmation to its selection, page lifetime and draft generation. Changes while reviewing require another review. For ordinary saves with no confirmation, existing click-time capture remains: later typing remains a newer local draft rather than changing the submitted answer. A new request that supersedes a preview makes the older token unusable. Save-size limits are checked before offering confirmation; no review history is silently removed to make a write fit.

Each affected node gains optional `reviewCauses: { changes, earlier }`. A cause records `sourceId`, `baseDigest` (SHA-256 of the normalized saved snapshot, not raw repository bytes) and `revision` of that pre-change base. The newest 32 distinct causes are retained; `earlier: true` explicitly represents additional/legacy unresolved causes. These are historical IDs and may refer to removed sources. Saving a reviewed answer acknowledges all causes present in that exact saved base; later guided review can use their individual identities. Structural acknowledgment clears its own causes. Separate upstream changes keep separate causes until acknowledgment, and old proofs cannot clear newer causes.

Optional `researchStale: true` is valid only with retained research. Both additions survive native/shared serialization, history and project copies; a project copy excluding research removes the marker. Private drafts, confirmation tokens and previews stay outside shared files. Unknown nested cause fields are rejected. Older shared clients reject these new fields rather than editing away their meaning; older personal readers may omit them. Use v0.1.81 or newer to preserve this information. The existing 9 MiB document bound also limits total provenance growth. Reduced visual exports omit cause identities; offline viewers include the research marker only when that research is explicitly selected.

## Verification

Behavioral tests cover read-only preparation, exact affected sets, bounded cause validation, unknown research dependencies, draft/content/proposal/expiry/identity freshness, final precommit checks, no-op and failed-save preservation, HTTP origin/size limits, paged paths and exact cancel/confirm editor behavior. Existing concurrency/research/save tests use explicit confirmation where the new behavior requires it. Native narrow-pane layout, keyboard and screen-reader flow, high-contrast themes and IME interaction remain pending owner verification; no browser or desktop automation was used.
