# Committed history and recovery

**History** lists saved revisions with their original update time, action label and checkpoint names. Select a revision to preview how many nodes change, return or disappear, whether guidance changes, and the complete saved content. **Restore this version** is an explicit action. **Undo** opens that same preview for the latest committed transition, including an intervening edit made by another canvas after refreshing. It never selects an arbitrary last edit by this particular canvas.

Restoring replaces the saved map's content, including answer states, review flags, research and sources, guidance, and finished state. It preserves the active journey identity and creation time. A content-changing restore creates a fresh increasing revision and update time, becomes another undoable change, and leaves its source snapshot immutable. An identical-content restore checks disk freshness, reports that the saved journey already matches, and creates no revision. The preview disables that unnecessary restore. Pending questions or research must be explicitly cancelled first; old callbacks remain invalidated. Restore does not restart generation.

Drafts flush under their original base before restore. Changed answers require an explicit recovery choice. Removed-question drafts retain exact text and state, including a visible state label for an empty draft. Failed draft writes block restore. Manual-question drafts must be saved or cleared before restoring. Surviving node IDs retain folds and map/editor view state; removed selections return to the root. Escape/Cancel closes History and returns focus to its opener. Native desktop appearance still needs manual verification.

## Identity, migration and budget

`history.mjs` stores history beneath `history/<key>/` inside the Explorer data root. Production keys are the stable library entry keys, so divergent legacy files with the same document ID stay separate. Direct-file previews use the draft identity: SHA-256 of canonical `realpath(file) + NUL + document.id`. A direct-file import with a new document ID begins a new history identity; the old directory stays preserved but is not offered in the new journey. A same-ID direct-file import is a recoverable change. Library imports/copies use their independent entry identity.

Old journeys need no rewrite. An ordinary open or history read invents no changes, sessions, or usage. Until the first edit/checkpoint there is no history manifest; the first preimage is labeled **Initial saved version**, using the original saved revision/time. Compatible missing schema defaults are normalized by the current document validator during preview/restore; incompatible snapshots are rejected. Original user whitespace, Unicode, state and research provenance are retained.

The retained history budget is exactly **50 snapshot revisions** and **134,217,728 bytes (128 MiB)** of serialized snapshot content per journey. The separate live document does not count. A named checkpoint of the live document stores a separate snapshot, which does count. There are at most **10 checkpoint names**, each **1–120 JavaScript characters**, non-whitespace, unique within the journey; the stored name is preserved exactly. Names are metadata, never filenames. Multiple names may protect the same revision and count individually toward ten names, while its snapshot counts once.

Oldest unnamed snapshots are pruned first, preserving every named revision and the latest undo preimage for an edit. The dialog reports the oldest retained revision; checkpoints can leave gaps. Removing a checkpoint removes its name/protection, not the document or necessarily the snapshot. If protection prevents safe pruning, the operation fails explicitly. With today's 9 MiB document limit, ten protected snapshots plus the latest preimage fit within 99 MiB/11 revisions; the defensive protected-only failure is not reachable with valid current-size documents. Tests exercise the planner's failure branch separately from actual valid-map retention.

The retained budget excludes manifests and temporary staging. A transaction can temporarily need one additional snapshot (at most 9 MiB), plus the atomic-write temporary copy and small metadata. An interrupted cleanup can leave obsolete files, but the next operation must finish that cleanup before staging another snapshot. Failures block subsequent commits; they do not accumulate successive successful edits beyond the bound. Unrecognized temporary files left by abrupt process death are preserved for manual inspection and are not retained history.

No drafts, voice/audio, full chat logs, pan/zoom or folding enter snapshots. History is absent from ordinary polling, exports, attached-chat context and isolated research context. Only the current committed document supplies those ordinary contexts. Snapshots are local history, not a cloud backup.

## Files and crash protocol

Each immutable `<sha256>.json` is a validated, pretty-serialized committed document; its hash covers its exact bytes. `manifest.json` is version 1 with `{ key, id, head, entries, undoRevision }`. Each head/entry has `{ revision, hash, bytes, time, label, checkpoints }`. Entries are strictly revision-ordered. `head` describes the active committed document, without storing another active copy unless checkpointed. A manifest is limited to 128 KiB. `intent.json` is limited to 256 KiB and has `{ version: 1, before, after, manifest }`: document hashes plus the proposed final manifest.

All controller history operations run through the existing transaction queue and the active document's exclusive `.lock`. They re-resolve library confinement/identity, validate the current file, and reject disk content/revision divergence. There is no multi-file atomic transaction. The protocol is:

1. Reconcile any old intent against the active document, validate retained snapshots, and finish old cleanup. Compute the retention plan before touching the document; never prune named snapshots.
2. Atomically persist the existing/baseline manifest. Store the immutable preimage. A preimage by itself is not a completed mutation and is never listed as proof of one.
3. Atomically write intent containing the pre/post hashes and planned manifest. Neither the old manifest nor old retained snapshots are destroyed before the document commits.
4. Atomically replace the active document. **This rename is the commit point.** Update the controller's in-memory document immediately.
5. Reconcile: if the active hash equals `after`, validate required snapshots and atomically install the proposed manifest. If it equals `before`, retain the old manifest. Remove the resolved intent, then remove validated unreferenced snapshots. If neither hash matches, preserve all files and report recovery required; never automatically overwrite the active document.

This also handles a crash after final manifest replacement but before intent removal. A pre-document failure leaves the old active document intact and retryable. A post-document finalization failure explicitly reports **Map saved, but history finalization failed**; the next History access or edit retries reconciliation. The new active document remains valid and the prior version remains on disk. Cleanup failure likewise reports the saved outcome and blocks further edits until cleanup succeeds. A checkpoint first establishes a baseline, writes a snapshot if needed, then atomically replaces only the manifest; it changes no document revision or usage evidence. A failure cleaning up after its manifest commit explicitly reports **Checkpoint updated, but history cleanup failed**.

The shared `atomicWrite` uses a unique same-directory `wx` temporary file and rename. It does not fsync files/directories or promise recovery after power loss, filesystem failure, arbitrary external writers, or coordinated tampering. The protocol covers interrupted application writes under the existing cooperative writer lock. Reconciliation never guesses an unknown outcome.

Snapshots, manifest/intent shapes, hashes, revision/time/identity, byte bounds and path confinement are checked. Symlinks/junctions and non-files are rejected. Full snapshot validation is cached per file stat identity/time/size and expected row metadata during one controller lifetime; changed files and explicitly requested previews are read and validated again. This keeps repeated near-limit edits practical. Missing manifests with existing snapshots are treated as recovery errors, not a new empty history. Corrupt/unreadable entries are preserved and block edits rather than silently replacing the map.

After fully exiting Copilot, back up the active `.explore.json` and the entire corresponding history directory before repairing/restoring a consistent backup. A missing or corrupt snapshot/manifest must be recovered from backup; do not delete intent to force an ambiguous outcome. Remove stale document `.lock` files only after Copilot fully exits. The UI provides errors and retry/refresh, not an automatic corruption-repair wizard. JSON/Markdown downloads still export only the active document; back up the data directory separately to preserve history.

## Controller and HTTP contracts

- `Explorer.readHistory(journey, snapshotRevision?)` runs under the transaction queue and document lock. `journey` must match `activeKey` (library) or `document.id` (direct-file). Without a snapshot it returns `{ journey, revision, pending, entries, current, undoRevision, oldestRevision, bytes, limits }`; entries are newest first, summaries only. With a snapshot it returns its metadata, `snapshotRevision`, current `revision`, `current` head, `pending`, `document`, and `preview: { matchesCurrent, removed, added, changed, guidanceChanged }`. `revision` always means the displayed current revision, never the selected historical one.
- `command('restore', { journey, revision, snapshotRevision })` checks the displayed revision against both controller and disk state, validates the snapshot under current schema, and uses the normal save boundary. It blocks pending work. `command('checkpoint', { journey, revision, snapshotRevision, name })` adds a name; `remove-checkpoint` accepts the same fields. Naming/removing names does not revise the document; operations serialize on its writer lock.
- `GET api/history?journey=...&snapshotRevision=...` is separate from `api/state`. The optional snapshot revision must be a canonical nonnegative safe integer. The route requires the instance token and exact Host. The three history writes use `POST api/action`, JSON, the client marker and exact Origin; the existing action-body cap is 10 MiB. Browser reads are bound to both their journey and request epoch, so delayed results cannot populate a switched/closed dialog.
- `History(directory, key, id, { write = atomicWrite }?)` is the focused persistence service. `list(current, requested?)`, `checkpoint(current, selected, name, remove?)`, `commit(before, after, label, replace)` and `reconcile(current)` assume the caller holds the document lock. `replace` must atomically save the supplied postimage; the controller owns revision/time assignment and active identity. `prune` is the shared exact-budget planner. The injectable write function supports deterministic failure testing without a runtime dependency.

Project journeys can retain multiple private history namespaces after explicit [external-change reconciliation](project-reconciliation.md). The active pointer is private; older namespaces remain protected and bounded Recovery discovery can inspect their saved versions.
