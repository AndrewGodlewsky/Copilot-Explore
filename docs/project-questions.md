# Project-aware questions

After approving a [project brief](project-context.md#reviewed-project-brief), choose **Project questions** on the journey root or a direction, or under a question's **More options → Explore** tab. Review the approved claims, saved map context, omissions and exact input strings, then choose **Generate project questions**. Opening the review starts no inference. Current implementation is context for inquiry, not a required future design. Claims retain their file-backed, inference, unknown or user-assertion labels.

The result enters the ordinary editable question preview. Accept only the questions you want. Generated interpretations never supply answers or change answer states. Existing answer drafts, caret and disclosures remain separate. Suggested wording and rationale can reflect the reviewed context and become portable map content if accepted; the raw brief, file excerpts, supporting quotes and prompt are not automatically saved with them.

## Ordinary generation and unavailable context

Existing Generate questions, Explore this direction and Explore deeper actions retain attached-session enqueue behavior. They do not include the project brief. **Use ordinary questions** in the project review explicitly selects that path. Ordinary follow-ups retain their existing saved-answer/state prerequisite; the review explains it when the selected question is unanswered. Unsaved text is never sent by fallback.

Off, missing, stale, unknown-only or unavailable project context cannot start project inference. The review explains the failure and offers ordinary generation or **Review project brief**. No failure silently switches execution routes or sends the project brief to attached chat. Changed context requires a new review; no automatic file refresh or model retry runs.

## Find files for a branch

Choose **Find branch files** in the Project questions review to open the existing scope dialog for that saved question or direction. An approved current brief is required. An optional short direction guides file suggestions locally; it is not an answer or an additional model prompt. **Find branch files** checks filenames and metadata through the same bounded discovery and exclusion rules as general discovery. It can find matching supported source files beyond conventional entry points, without reading new file contents or invoking a model. Previously approved contributing files can be reread for freshness.

Suggestions use literal Unicode word matches from the saved target/answer, ancestors, approved brief, objective and pins, plus known sources of reviewed shared constraints. Reasons identify each match; they do not verify semantic relevance or turn uncertain claims into facts. Direction and target matches rank first, then shared-source, ancestor and broader brief matches. Results remain limited to 40 candidates from the existing bounded traversal. The suggested selection fits the five-file, total-read and total-excerpt budgets. Partial discovery, other candidates and shared-source omissions are disclosed. Missing files, unfamiliar naming or a branch without code can produce no useful match; ordinary questions and manually validated paths remain available.

Viewing suggestions keeps the current brief approved. **Use suggested files** explicitly replaces the selected paths and revokes the old scope. Remove irrelevant files, then review and enable the exact scope, choose **Read reviewed files**, review the new brief request, generate the brief and approve its claims. Same-project user corrections remain labeled assertions; omitted file-backed constraints need review in the replacement brief. Only then can another Project questions request consume those new claims. Raw excerpts never bypass brief review into question generation. **Return to project questions** preserves the answer draft and offers ordinary generation as before.

Discovery binds to the approved brief and contributing saved branch/guidance data, rechecking after asynchronous work. Changed approval, root or branch inputs reject late suggestions. New or manually entered paths still pass canonical/secret/ignore/size checks at scope review and read. Later question requests retain the exact selected-file/brief freshness checks above; unrelated unselected file edits do not discard a valid result. Suggestions and their direction remain transient local UI/controller state, outside saved maps and exports. No continuous scan, web access or repository mutation is added.

## Why this question?

Expand **Why suggested?** in a project question preview, or **Context & navigation → Why this question?** after acceptance. Each question cites one to five claims from the exact approved brief. The explanation labels **File-backed interpretation**, **Inference**, **Unknown** and **User assertion**, showing only validated relative filenames where the reviewed claim has file evidence. These are model-selected reasons for the original wording, not proof, confidence scores or new decisions. Supporting quotes and line numbers are not copied into the explanation. Adjusted wording keeps its original explanation.

Choose **Dismiss preview & review brief**, or **Review project brief** on an accepted question, to correct or remove claims using the existing brief editor. Approve the corrected brief, then choose **Return to project questions** to explicitly review a new request for the original parent. Generation and acceptance remain separate. Existing questions and saved answers are never replaced or deleted, and the answer draft stays intact. If another preview is open, dismiss it before starting a replacement request.

Explanations use the already reviewed brief in this canvas; opening a disclosure does not read or open a file. Revocation, changed/missing sources and replaced brief approvals make references **stale**. Reopened/imported maps show **unavailable** context because they retain only a generic project-origin marker, not private claims or filenames. A new brief cannot silently substitute its facts for an older explanation. Freshness means current at the last scope/policy check, not continuous filesystem monitoring; operation boundaries still perform full source checks. Canonical checkout changes also revoke approval. Use the [explicit refresh comparison](project-context.md#refresh-project-context) before reusing project context.

## Request and helper boundary

`project-questions.mjs` projects at most 50 approved claims as ID, section, text and kind, bound to the approved brief revision. It includes all projected claims as required context; supporting file quotes, full excerpts, absolute root and private editor text are excluded. The existing relevance selector adds saved map decisions, uncertainty and child-question coverage. Actual SDK instructions plus prompt are bounded to 128 KiB UTF-8. Exact review reports optional omissions. An unknown-only brief is insufficient; user corrections can provide useful context without becoming file evidence.

The `project-questions` review token is one-use, purpose-specific and expires after ten minutes. Scope/read, Project Brief, Research, Challenge and regeneration tokens cannot substitute for it. The helper uses the selected eligible Copilot chat model, matching account checks, isolated empty working/configuration directories and zero initialized tools. Dedicated Research model settings do not apply. Ambient instructions/skills, repository tools and web retrieval remain disabled. The model provider receives the reviewed inputs and normal Copilot usage applies; tool-free is not offline.

The helper shares the existing tool-free execution queue and confirmed-shutdown barrier. It has the existing 180-second operation allowance; shutdown/accounting can continue afterward. Cancellation stops only this owned helper. Content-free usage receipts are labeled **Explorer Project Questions**. Attached-session native callbacks, including failure callbacks, cannot fulfill this owned request.

Output is strict JSON with one to six questions, category, rationale, importance, importance reason and `claimIds`. Each question must reference one to five distinct IDs in the exact reviewed brief. Both the helper parser and controller validate references, including injected helper results. Missing/unknown/duplicate IDs, arbitrary file paths, unknown keys and answer fields reject; existing question length, duplicate and acceptance limits also apply. The controller stages the result, never commits model output automatically. No new native model-callable acceptance action exists.

## Freshness and retention

Private approval guards bind the brief revision/object, canonical project/checkout capture, journey and workspace epoch. Full selected-file/policy freshness is checked before review, before queued dispatch, after the result and before acceptance, including the final asynchronous source check before saving. Saved map contributors and scenario policy are rechecked too. Revoking the brief or disabling scope cancels relevant pending work and makes an existing preview stale. Changed roots, files or map inputs cannot silently produce accepted new questions.

Brief inputs, review tokens, helper work and private source guards remain in canvas memory, outside maps, history, native snapshots and exports. A cancelled helper can retain already sent inputs until shutdown; a stale preview retains its private validation state until dismissal/replacement or canvas close. Native SDK/provider logs may retain inputs (#41), and transport enforcement remains limited (#42). Turning context off prevents future use; it cannot retract already sent inputs.

Accepted questions retain only `generation.source: "project-brief"` as historical origin. This marker is validated but is not trusted evidence: importing one cannot retrieve private context. Current-canvas reference bindings match journey, node, request and original wording/category, and are tied to the exact approval object. Browser-only map polling carries IDs, capture identity and revision; labels/text/files are resolved against the matching approved local brief. No private claim/source text, paths or supporting quotes is added to map polling through this metadata. Private references are omitted entirely from shared files, history, native context and exports. Accepted question wording and rationale can themselves reflect the reviewed context, as disclosed before acceptance.
