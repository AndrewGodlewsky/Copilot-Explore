# Research context review

**Research** opens an inline review in the selected question's bottom drawer before any research helper starts. This explicit action expands the existing drawer to make room for reading; Reduce remains available. The complete literal question, saved answer state, mode, objective, included/omitted record counts, a short sample of prior records, effective model, source behavior and effort appear first. The unsaved answer draft is explicitly excluded. **Effort and source preferences** reveals optional controls; **Exact inputs, exclusions and omissions** exposes complete required guidance, pins, target and optional records, byte counts, omission reasons and the exact instructions/prompt. Expanding these disclosures starts no work and does not change the reviewed inputs.

Required target/guidance/pins cannot be excluded. Optional exclusions, effort/source preferences, a changed scope or a saved Research model preference refresh the preview and invalidate the old token before **Research** can start. Typing an excluded unsaved draft does not refresh it. Disclosures and control focus survive refresh; previous inputs retained during preparation or failure are explicitly marked unusable. Exclusions are request-local, never saved as guidance or answers.

Editing a follow-up question or its hypothetical flag dismisses its unused review, including one still preparing. Choose **Review follow-up context** again to review the changed request. The composer stays mounted and focused during typing or composition; editing the next question while already-started work runs does not cancel that work. If another writer removes the selected question, its unused review is cancelled before the drawer is removed, while a locally saved answer draft remains recoverable.

The source summary separates reviewed input sent to the model provider from external search/page requests, which remain subject to host permissions. Current Research uses the existing search/fetch route; help without new retrieval is not yet available here (tracked in #104). Moving the review does not implement a new source mode, change permissions, or resolve #41/#42's logging/transport requirements.

**Back** or Escape dismisses the unused review and restores its launcher; a select keeps its native Escape behavior. Leaving the tab, closing the drawer, changing the node/journey, collapsing the question, opening Home or suspending/reloading the page cancels an unused review and rejects delayed replies. **Answer draft** keeps the review and discussion while reducing the drawer and focusing the same mounted editor. No second editor or focus trap is introduced. Already explicitly started work keeps the separate **Cancel request** control. Challenge Review and regeneration retain their separate modal flows and exact-input contracts.

The exact instructions and prompt are available as literal text. Ordinary research excludes historical AI rationale, prior research, raw drafts, private visual references, history and audio. No project files or source attachments are included. User statements and answer states are not verified facts. This controls only Explorer's input to the isolated research helper, not earlier main-chat context or the separate native `get_exploration` snapshot. Reading a review does not start a model, initialize web tools, request permissions or change the host model.

Choose **Quick** (60,000 milliseconds / 8 tool attempts), **Standard** (180,000 milliseconds / 24 attempts, the default), or **Deeper** (300,000 milliseconds / 40 attempts). The elapsed allowance starts when owned execution begins, including runtime, account, model and tool setup. A queued wait for an earlier helper's release does not spend the next allowance. The owned operation timer is authoritative; research no longer uses the attached-question controller watchdog. The send wait receives only the remaining allowance. Each pre-tool invocation counts, including denied calls; the first N attempts may proceed if otherwise eligible, while N+1 is denied and invalidates outstanding approvals. Post-lookup permission and tool approvals recheck cancellation and the deadline. Started RPCs may finish after cancellation; bounded shutdown and usage accounting may continue beyond the elapsed limit. This is not a hard process-wall-clock completion promise.

**Balanced evidence** (default) prefers original or official sources for factual claims while allowing secondary context. **Prefer primary sources** prioritizes original studies, official documentation and direct provider evidence. **Prefer recent sources when relevant** is optional qualitative retrieval guidance; the default has no recency preference. These choices do not guarantee availability, freshness or accuracy. Unknown publication dates remain unknown, and useful older foundational evidence is not automatically discarded. They do not widen map scope or override exclusions. Changing preferences refreshes the actual preview and replaces its token before a new explicit Start.

The immutable preparation includes validated `settings: {depth, sourceFocus, recency}` and derived `limits: {timeLimitMs, toolAttemptLimit}`. Depth enum meanings have the fixed ceilings above; source focus is `balanced|primary`, recency is `any|recent`. The chosen settings enter exact measured instructions and runtime gates. Saved research retains settings from the trusted captured request, overriding model-reported values. Import, history and Markdown preserve them; older research without settings stays absent and displays unknown, never assumed Standard. These are requested limits and retrieval preferences, not measurements of actual elapsed time, evidence quality or tool count. Existing operation-specific usage receipts remain separate and unchanged.

The existing 131,072-byte ceiling counts UTF-8 bytes in the actual instructions plus prompt, including JSON escaping and selection guidance. Optional records are omitted whole. Required target, guidance and pins are admitted first. Ordinary research and follow-ups rank optional records across branches in this order:

1. Explicit prerequisites of the target or its ancestors, including transitive prerequisites and unresolved unanswered questions. Closer dependency steps rank first within this group.
2. Literal matches to pinned constraints, then objective/success criteria, then the target question or saved answer.
3. Ancestors, then remaining questions with a saved answer or non-unanswered answer state.

Within equivalent relevance, needs-review answers, assumptions and unresolved evidence precede tentative and settled decisions; tree distance and stable ID break remaining ties. Included ancestors retain their original path order in the payload even when admission prioritizes a distant prerequisite. Path-only scope still excludes other branches, including their prerequisites. Explicit exclusions apply to all optional records; the target remains required. A record that does not fit is skipped whole so smaller later records can still fit. Scope, explicit exclusions and budget omissions have separate counts. Mandatory overflow remains an error. Exclusions may free space for other whole records; inspect the updated preview before starting.

This is a deterministic heuristic, not semantic search or proof of relevance. It compares normalized Unicode letter/number tokens of at least three characters with a small English stopword set. Short words, synonyms and languages without word spacing may match poorly. Graph links are user assertions, not verified causal relationships. Selection reasons accompany included records, and the exact selection policy appears in the local review and measured model input. Answer state and needs-review flags remain intact; conflicting, tentative and unanswered records are never promoted into confirmed constraints. Scenario metadata keeps its existing hypothetical/unselected labels. Only the current saved map participates; historical or superseded scenario files are not retrieved implicitly. Attached question generation, summaries, regeneration and tool-free Challenge Review retain their separate context contracts, including Challenge's explicit selected-file boundary.

The review also shows a human-only omission sample: up to 50 complete question descriptors and 32,768 serialized UTF-8 bytes, with ID, question, answer state, selection reasons and whether scope, exclusion or budget omitted the record. It contains no omitted answer text and is never sent to the helper. A question too large for the remaining sample space ends the sample without truncation. The total and remaining count explicitly identify records beyond the sample. These bounds supplement the existing review-response limit; they do not expand the model-input budget.

`POST api/research-review` requires exact Origin, the instance URL token and `X-Explorer-Client: 1`. Its input fields are `action` (`prepare` or `cancel`), `clientId`, monotonic `sequence`, `journey`, `nodeId`, `scope`, `excluded` and optional `settings` (omission uses Standard/balanced/any for this new request). Unknown fields or unsupported settings reject. IDs follow the existing map limits (100 UTF-16 code units); there are at most 5,000 unique exclusion IDs. Requests are capped at 512 KiB and serialized JSON review responses at 1 MiB, separately from the actual input-string budget. Large escaped exclusion lists can exceed these transport limits even when their content would otherwise fit.

Each canvas retains one deeply frozen preparation, one latest client/sequence marker and a ten-minute expiration timer. A newer prepare replaces the prior token. Cancellation keeps the latest sequence marker to reject late prepares from that client; closing clears payload retention. Tokens are opaque, single-use, server-owned and bound to journey/node, file/library key, exact transmitted source records and saved research destination. No private review state is added to native snapshots or conditional public polling.

The protected `research` action requires the token plus journey/node. Under the existing document lock it rereads current disk state and compares the captured source and destination values. Relevant changes consume the review and require an explicit refresh and start; unrelated changes do not cause a blanket revision rejection. The controller passes the captured instructions and prompt to the helper verbatim. Completion still merges only research into the latest disk document and checks source/destination ownership and actual helper release. Attached-chat question generation keeps its separate preparation and historical generation-context behavior.

For ordinary research, freshness also recomputes relevance under the reviewed scope, exclusions, scenario and exact reserved instruction/prefix byte count. It compares the actual selected records and their reasons, not the global revision or omission counts. New explicit/literal relevance can invalidate a request when it changes the selection. Previously sent unrelated fallback records remain contributors, while newly answered unrelated fallbacks and previously omitted fallbacks do not enter an in-flight request simply because they now fit. A new explicit preview considers them normally. Removed or cleared exclusions do not invalidate unchanged contributors. Full candidate counts still participate in exact byte accounting; a metadata-size change that actually changes which records fit requires a fresh review. No live prompt is silently replaced.

Native narrow-pane appearance, keyboard feel and live research quality require manual verification. HTTP/jsdom and installed local SDK fixtures verify protocol, literal rendering, editor preservation and exact input strings without a paid provider, real microphone or existing user session.

## Scoped follow-ups

After research, **Ask about this research** accepts a clarification, a question about the recommendation, or a hypothetical change. The complete nonblank question is limited to 4,000 UTF-16 code units, preserving whitespace and Unicode. The hypothetical checkbox labels the inquiry; any changes described in a question remain hypothetical regardless of that checkbox. Follow-ups never commit constraints, answers, answer states, guidance, a decision brief, or replacement research. Use the existing answer/guidance editors to commit a decision yourself.

**Review follow-up context** uses the same local, immutable, single-use ten-minute ResearchReview token and explicit Start. The optional `followup: {question,hypothetical}` field selects this purpose; a token cannot be used for the other research purpose. The protected `research-follow-up` action shares the ordinary research queue and unconfirmed-release barrier in both directions. Each request creates and stops its own isolated helper, with the same selected Quick/Standard/Deeper elapsed and attempted-tool ceilings, permission/account/model/tool checks, deadline rechecks and retained accounting. Queued release wait is not execution time. Receipts and recovery identify `research-follow-up` / `Explorer Research Follow-up`; diagnostics retain the ordinary web-research prerequisite and release checks. No inference retry, parallel helper pool, attached-chat turn, changed model, or persistent conversation database is introduced.

Mandatory input is the exact current question and hypothetical marker, the complete original recommendation, and the existing committed target/identity/guidance/mode/pins. Optional original evidence is one complete claims-and-sources record, followed by summary, uncertainty and each complete option. Newest retained complete exchanges are then considered, displayed chronologically. Optional committed ancestors and other answers use the remaining budget. Each rejected optional record is omitted whole; coverage separately counts original records, retained exchanges, previously dropped exchanges and ordinary context scope/exclusion/budget omissions. The original research may legally exceed the 131,072-byte actual instruction-plus-prompt limit: it is never blindly copied or sliced. Mandatory overflow fails locally before inference. The preview displays exact strings, included records, counts and source-tracking bounds. The same 512 KiB review request / 1 MiB response transport caps apply.

One transient history belongs to the canvas's active journey/node and exact original research. It retains at most four complete exchanges and at most **65,536 serialized UTF-8 bytes**, counting questions, results, UUIDs, hypothetical flags, JSON escapes and trusted source metadata. Oldest complete exchanges are dropped until both limits fit, with a cumulative visible count. No full research or prepared context is duplicated per exchange. A separate single source-dependency snapshot stores SHA-256 fingerprints of the original research, identity, framing and a union of all actually transmitted committed records and their relevance reasons. These unions include earlier exchanges even if their records are excluded on a later request; each is capped at 5,000 IDs, with the entire snapshot capped at 4 MiB serialized bytes. Preparation exposes its actual record count/bytes and fails before inference on overflow. One pending immutable preparation and one active helper remain separately bounded by the existing reviewed-input limits.

Current-disk comparisons run under the document lock at start and before accepting a result. Changes to original research, any previously transmitted source or its selection reasons invalidate pending results and permanently mark the retained history historical once observed; a new explicit request starts a fresh chain. Unrelated metadata changes preserve it. Omitted records are not retrospectively treated as previously read history; changed membership is checked for the current prepared request separately. Request IDs, journey/node identity, review purpose and history identity reject stale or duplicate completions. Original research and answers are never rewritten by follow-up completion.

Node navigation hides history; a successful follow-up on another node replaces the one retained history. Canvas close/restart or journey switching discards it. A web-panel reload clears the unsent typed question but may reconnect to pending work and completed history while the same canvas controller remains alive. Already started work continues until completion, cancellation or canvas close; reload never starts an additional request. Late responses from the old page are ignored. There is no export or durable recovery of follow-up text. Existing retained usage/recovery receipts remain available independently.

The response is exactly `{answer,uncertainty,claims,sources}`. Answer allows 5,000 and uncertainty 3,000 UTF-16 units, both nonblank. Raw JSON is capped at **12,000 UTF-16 units and 24,576 UTF-8 bytes**; trusted normalized output is also capped at 24,576 serialized UTF-8 bytes. Claim/source counts, field limits, result-local IDs, canonical URLs and evidence relations reuse the claim validator below. No fake comparison/options are synthesized. Field maxima do not override total limits. Sources and uncertainty remain inspectable next to each claim; all text is literal and links use validated HTTP(S) URLs.

For prior evidence, model output uses `{id,prior:{origin,sourceId}}`, where origin is `original` or an included exchange UUID. Only sources actually included in that original evidence record or complete exchange resolve; omitted/unknown origins or IDs reject. Trusted parsing copies the original title, URL, retrieval time and imported/recorded provenance unchanged, attaching the explicit prior origin. It does not add that URL to this request's successful-read map. A new source uses `{id,title,url}` and must have an eligible successful read in this request; the hook supplies its time and recorded provenance. New unsupported factual assertions must be labeled reasoning or unknown. Source IDs are local to each result; identical IDs in different exchanges do not cross-resolve. Prior imported dates remain imported metadata, never a newly observed fetch. As with ordinary research, positive fetch/time evidence is deterministic hook coverage; the installed fixture proves MCP search, prior metadata preservation and rejection of an unread new source, not successful built-in fetch transport or live model relevance.

## Claim evidence

New research contains 1–12 selected model assertions in `claims`. Each has a stable result-local `id`, `text`, `basis` (`sources`, `reasoning` or `unknown`), `evidence` and `limitations`. A sourced claim links 1–3 distinct known source IDs with concise supporting paraphrases; reasoning and unknown claims have no evidence links. These are model interpretations, not an exhaustive check of every sentence in the summary, options or recommendation. Reading a page does not establish that it supports a claim or that a claim is true. No confidence percentages, direct quotations, entire pages or additional fact-checking agent are retained.

There are at most 15 sources, each with a unique ID and canonical HTTP(S) URL. Claim and source IDs use separate namespaces, match `[A-Za-z][A-Za-z0-9_-]{0,31}`, and remain unchanged through storage/history/export. Claim text, supporting paraphrase and limitations each allow at most 1,000 UTF-16 code units. Source titles allow 300; raw and canonical URLs each allow 2,000. Unknown evidence fields, duplicate IDs/URLs, unknown/repeated references and a claim basis inconsistent with its evidence reject the result. Existing option/recommendation/draft field maxima remain unchanged. Field maxima cannot all be used at once: model output retains its 80,000 UTF-16-code-unit ceiling and adds a 160,000-byte UTF-8 ceiling, including JSON escapes. Evidence-bearing saved research also has that 160,000-byte serialized cap before and after normalization, including captured settings/read metadata. The whole journey remains bounded by 9 MiB. Oversize or malformed results fail without clipping evidence or replacing previous research.

The owned request records the first eligible successful `web_fetch` completion with a matching tool-call ID and nonblank `textResultForLlm` for each requested URL. It records the wall-clock ISO UTC time at that callback, never a model-supplied time. Fragments are removed; query strings remain significant. Search snippets, failures, blank results, unmatched/reused IDs and prior-request reads cannot substantiate sources. Failure callbacks discard their pending read; cancellation/deadline prevents late success capture. Only requested URL identity is observed here: redirect destination and publication date remain unknown. Page content is not stored in the journey. The bounded request-local read map is discarded with the helper; later transport work can supply the same successful-requested-URL/time observation without changing claim relations.

Persisted sources have `retrievedAt` and `provenance: recorded-read|imported`. `recorded-read` timestamps originate in this helper's tool hook; model times/origin are overwritten before validation and cannot credit an unfetched source. Explicit external import changes provenance to `imported`, preserving any valid historical date as supplied metadata, not observation by this installation. Imported metadata may use `retrievedAt: null` when the time is unknown. An identical existing local record is returned unchanged before any import transformation; divergent same-ID imports require a separate copy. Ordinary reopen, validation and history restore preserve existing provenance. Native files are editable user data, not cryptographically attested receipts. Legacy URL lists remain lists with unknown claim support and historical retrieval times; no migration invents IDs, dates or evidence.

Each claim's keyboard-accessible disclosure shows its model basis, supporting paraphrase, source link, recorded/imported time and limitations alongside the claim. Text remains literal and only validated HTTP(S) URLs become links. Complete Markdown escapes content and retains claims, references, timestamps and origin; native exports and history retain the validated schema. Existing explicit suggestion actions still edit only a draft; the user alone saves an answer.

Deterministic hook fixtures prove successful read/time attribution, ID matching, failure, cancellation and request isolation. The installed local SDK fixture separately proves real MCP search, rejects a fabricated source and model timestamp after search alone, returns reasoning/unknown claims, and retains completed/failed usage receipts. It does **not** exercise successful installed built-in `web_fetch`; no production private-URL exception was added. Live source quality, redirect transport and native visual/keyboard feel remain outside that fixture's evidence.

## Reviewed model

The review shows the effective model and whether it follows the selected chat or a dedicated personal choice. Model/account and preference freshness are checked again at Start; accepted operations keep their captured model. Settings and metadata review start no inference. See [Research model](research-model.md) for unavailable choices, private storage and verified-model receipts.
