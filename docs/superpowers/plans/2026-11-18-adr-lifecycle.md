# ADR lifecycle implementation plan

> Use superpowers:executing-plans inline, task by task, with one independent final reviewer. The owner authorizes sequential implementation and publication to main.

**Goal:** Explicitly approve, deprecate and supersede associated ADRs while preserving the original decision, source capture and interrupted-write evidence.
**Spec:** #85, with #86 successor-proposal compatibility. Baseline 5a4b791ad97079178b342ce898a34953c3a5fd27, v0.1.101. Prerequisites #80 and #84 are closed.
**Architecture:** A bounded lifecycle contract extends ADR associations. Pure Markdown transformations touch generated status/reference metadata only. A private coordinator reuses guarded single-file publication for one or two reviewed files and saves reciprocal associations together. The existing ADR dialog exposes explicit lifecycle review and recovery.
**Tech stack:** Existing Node ESM, filesystem guards, plain browser modules, node:test/jsdom; no new runtime dependency/model/Git writes.

## Exact interfaces

- `validateAdrLifecycle(value, status)` normalizes exactly `{version:1,events,predecessor,successors,supersededBy}`. Events are exactly `{from,to,actor,at}`, at most three legal transitions from the initial proposed state; dates are valid canonical ISO strings and nondecreasing. References are exactly `{id,path}`. At most 49 unique successors and 32 KiB of lifecycle metadata are allowed. Non-proposed records require lifecycle metadata; old proposed records may omit it.
- `validateAdrRelationships(records)` checks the complete normalized association graph, including reciprocal matching paths, no self/cyclic links, one accepted replacement, and consistency of `supersededBy` with the final statuses and event history. It does not read files or infer approval.
- `changeAdrLifecycle(records, {kind:'accept'|'deprecate',id}, event)` returns the complete validated next record list. A successor acceptance updates its predecessor in the same result. `linkAdrSuccessor(records, predecessorId, successor)` adds a new proposed record and reciprocal references without status events or decision approval. The predecessor must have reached accepted and must not already be superseded.
- `associateAdrBatch(existing, pairs)` takes one or two `{record,base}` pairs, validates every expected base, applies them together, then validates the complete graph. `associateAdrFile` retains its existing single-record behavior by delegating to the batch operation.
- `adrLifecycleFooter(record)` returns literal generated lifecycle Markdown or an empty string for legacy records. `appendAdrLifecycle(content, record)` appends it before the original managed marker in freshly generated proposed content. `transitionAdrMarkdown(content, before, after)` verifies the original digest/marker/footer, changes generated status metadata only, and appends the new footer. Both keep the 64 KiB file bound. The caller records the resulting byte digest.
- Status metadata rendering handles the existing generated `status` frontmatter, a supported Status heading when present, and the fixed status notice. It never rewrites question/decision text merely containing a status word. The footer lists events, predecessor, successor alternatives and the actual superseding record separately.
- `AdrFileStorage.complete(id, associationGuard)` adds an optional `completed:true` terminal receipt only after publication/cleanup and the caller's saved-association proof. New intents carry `completionRequired:true`; a missing completion receipt stays pending and requires explicit reconciliation. Legacy intents without that requirement retain their existing interpretation. The historical intent remains; completed intents cannot publish or abandon again. `validateAdrWriteIntent` exports the existing strict intent validator for coordinator child plans.
- `AdrLifecycleStorage({readRoot,directory,key,lockDirectory})` provides `readIntent()`, `begin(value,previousId=null)`, `child(intent,index)`, `states(intent)`, `publish(id,guard)`, `complete(id,associationGuard)` and `abandon(id)`. `value` is exactly `{kind,journeyId,sourceDigest,actor,steps}`; kind is `accept`, `deprecate` or `successor`. One or two steps are exactly `{target,content,record,base}`. The private normalized intent adds `{version:1,id,createdAt,abandoned,completed}` and is limited to 1 MiB. Target roots must match and paths/record IDs must be distinct.
- Child identities derive from the trusted journey key, batch UUID and index. Reuse an existing child only if its immutable plan matches; permit only the original parent-identity prefix plus guarded newly created parents. Child states report observed publication/cleanup or unavailable state, never inferred success from content equality. Publish checks all parts before its final source guard; completion persists only after all parts and the association are proven. A completed batch stays historical after later legitimate file/association changes.
- New `api/adr-lifecycle` requests route through `controller.adrLifecycleRequest`. Exact action schemas mirror ADR file review: status `{action,journey}`, prepare `{action,journey,clientId,sequence,selection}`, cancel `{action,journey,clientId,sequence}`, save `{action,journey,token,revision}`, reconcile/discard `{action,journey,operationId,revision}`. Selection is `{kind:'accept'|'deprecate',id}` or `{kind:'successor',id,number}`. Bound requests to 16 KiB and serialized responses to 512 KiB; oversized exact previews reject before issuing tokens.

## Contracts and constraints

- Existing proposed adrFiles v1 records remain valid without lifecycle metadata. status supports proposed, accepted, deprecated, superseded; wording acceptance, scenario choice, answer state, imports and refresh never transition decision status.
- Optional lifecycle v1 has events, predecessor, successors, supersededBy. Each status event records from/to plus validated nullable contributor actor and exact ISO timestamp. Legacy proposed creation uses existing writtenAt without inventing actor. References have validated stable UUID and recorded Markdown path. Lists/graph are bounded by50 associations, unique and reciprocal, paths match associated records, cycles rejected. Only one successor can supersede a predecessor; alternate proposed/deprecated successor records remain historical.
- Legal transitions: proposed->accepted or deprecated; accepted->deprecated or superseded; deprecated that previously reached accepted may be superseded by an explicitly accepted successor; superseded terminal. No rollback or silent re-acceptance. Same-operation replay is idempotent. Same-status new requests are rejected or clearly no-op, never duplicate events.
- Creating a successor writes a NEW proposed ADR and records reciprocal references while keeping predecessor status. A separately reviewed acceptance of that successor sets it accepted and predecessor superseded together. Proposed successor alternatives can be deprecated without erasing links. Do not accept another successor of an already superseded predecessor.
- Normal substantive updates are limited to proposed records and preserve their lifecycle links. Accepted/deprecated/superseded decision/rationale and original source captures never regenerate in place; new reasoning creates a successor proposal. Changes to status/reference metadata are fully previewed, retain uncertainty and do not mutate answers.
- Markdown transitions preserve all substantive bytes and captured source appendix. Update only generated status frontmatter/heading/fixed notice and an exact generated lifecycle footer. Keep existing managed UUID marker as identity metadata; document that it is not lifecycle authority. Guard original bytes and generated-footer consistency before changes. Test templates with status frontmatter, status heading and omitted status.
- The lifecycle private intent records exact reviewed files/records/bases and source proof, one or two operations only. Reuse AdrFileStorage per child with trusted derived keys. Persist coordinator before writes; retry identifies the same child intent rather than replaying another write. Never infer authority from stored absolute paths; revalidate fresh working root and original shared Git-root ADR locations.
- Publish a new successor before changing predecessor references. Acceptance/supersession must expose separate observed file outcomes. Before each unpublished operation, check source/association/identity and destination bases; recheck source after asynchronous storage preparation. Stage/cleanup guards stay intact. Document cooperative filesystem/CAS limits; no global atomicity claim.
- Atomically save all resulting associations only after every file is verified published/clean. Reconciliation preserves published files, original captures and newer unrelated answers. Source changes before any publication reject replay. Once partially published, only explicit reconciliation of the exact historical operation may finish metadata/associations; conflicting file/association bases stay unresolved. Discard only when no child is published, never delete/roll back published files.
- Block conflicting ordinary ADR writes while lifecycle recovery is unfinished, and lifecycle writes while ordinary file recovery is unfinished. Preview/cancel alone must create no project files or private write intent. Timeout/close cannot cancel a confirmed publication or claim nothing saved.
- Preserve durable completion receipts across those workflows. A later legitimate status/content change must not make a completed older intent appear unfinished. A durable association whose completion receipt failed still needs explicit reconciliation before another conflicting operation. Historical completion is distinct from current file content verification.
- HTTP actions use exact schemas, active journey/revision, explicit current token, bounded response, Origin/token checks and serialized document locking. UI uses literal text, accessible labels, complete before/after previews for both files, explicit status intent and source uncertainty, invalidates stale/hidden replies and retains private answer drafts.
- Attribution uses only the existing optional self-declared contributor setting, never Git/system/session metadata. No model calls, external research, commit/push from product UI or project-wide ADR register.
- Release v0.1.102. Synchronize all metadata, release note<=400chars, full tests/check/package, runtime fixture if host integration changes, exact remote main verification and issue completion comments. Native UI checks owner-only; no browser/desktop automation. Retain ignored audit notes after earlier cleanup rejection.

## Review focus
- A proposed successor must not accept itself or supersede the predecessor through generation, wording acceptance, refresh or incomplete publication.
- Partial two-file publication must retain original decisions and expose recoverable exact historical intent despite newer source answers or process restart.
- Imported/reordered records, alternate/deprecated successor proposals and competing acceptance must not create cycles, dangling relationships or two accepted replacements.
- Nested working roots, same-named copied files and final asynchronous source/destination changes must preserve prior bytes and refuse stale authority.
- Custom status layout and user text containing lifecycle-like words must not cause substantive content replacement; source uncertainty and historical captures remain visible after transitions.
