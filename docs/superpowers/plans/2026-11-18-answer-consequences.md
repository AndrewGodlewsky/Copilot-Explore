# Issue #66: answer-change consequences

Use the existing DecisionImpact traversal for both preview and invalidation, including structural directions and mixed paths. Keep an exact proposed answer/state and full saved-content digest, journey/file identity, draft revision, expansion intent and pending/staged-work identity behind an expiring, single-use confirmation token. Prepare and paged inspection are read-only. Confirm under the existing document lock and recheck immediately before atomic replacement. No-impact saves and no-ops remain lightweight. A stale confirmation fails without clearing drafts.

Persist bounded review causes on affected nodes: upstream source ID, saved-base digest and revision, with an explicit overflow marker instead of pretending truncated causes are complete. Preserve legacy review flags as an unknown earlier cause. A current explicit answer save acknowledges the causes present in that saved base; later guided review can use individual cause identities. Mark retained research as stale separately so acknowledging an answer does not imply its research was refreshed. New research clears that marker. Export/import and strict shared validation preserve these fields; old shared readers reject them.

Add an accessible modal before consequential saves, with exact current/proposed text and state, counts, 50-item pages and 30-step paths. Include retained research, generated questions, staged questions and active research affected by the saved-context change. ADR associations are unavailable. Cancel retains draft text/state/caret. Reject changes to the draft, selection/journey or saved/pending source while the modal is open; no automatic confirmation. Ordinary leaf saves do not show a modal. Existing atomic save, history and owned-helper cancellation remain authoritative.

Tests: pure affected-set equality and provenance bounds/validation; controller preview immutability, no-op history, cross-branch effects, stale token/draft/file/proposal, failure before commit, single use; HTTP origin/input bounds; jsdom cancel/confirm/paging/draft and modal freshness. Run full tests/check/package, installed fixture if integration changes; independent final review and fix material findings. Patch version and publish/verify main.
